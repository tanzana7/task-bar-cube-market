# Grade判定と市場更新の運用

## Gradeの根拠

保存済みの131商品（全191観測）を再集計したところ、先頭語は20種類あり、`Arcane`、`Cobalt`、`Rusty`、`Celestial`などの名称が含まれる。Steamの市場名とqueryActionレスポンスには、Gradeを示す独立した属性が保存されていない。名前の素材・品質語とGradeの対応を示すTask Bar Cubeの公式アイテム表も、確認した公開情報にはなかった。

[SteamのTask Bar Cubeストアページ](https://store.steampowered.com/app/5084200/Task_Bar_Cube/)は「CommonからDivineまで7段階のrarity」とゲーム全体の範囲を示すが、個々のMarket商品や名前の接頭語との対応は記載していない。この記述はGrade階層の存在を裏付けるだけで、`Rusty`等のGradeを特定する根拠にはならない。

そのため、商品名の先頭にGrade名が明示されている場合だけ分類し、その他はunknownのまま扱う。公開済み131商品はGrade 0/131、Type 131/131、Quality 126/131。Gradeフィルターと最低Gradeは、データ中に分類済み商品が1件もない間は無効化し、「Grade情報未取得」と表示する。Steamストアは7段階の存在を確認する一次資料だが、商品別対応表は未確認であり、素材prefixの辞書登録は行わない。

Grade辞書を追加する際は、公式ゲーム内表示または開発元の一次資料に基づいて対象商品/系列、Grade、根拠、URL、確認日を記録する。Task Bar Heroやコミュニティ由来の対応表はTask Bar Cubeの証拠として流用しない。

## おすすめ評価

バランス評価の元の比重はGrade 45、Quality 35、価格20。各候補では未取得属性を除外し、候補自身に有効な項目の比重合計でスコアを正規化する。表示する「評価」内訳はその候補で実際に使用した比率である。たとえばGradeなし・Qualityあり・価格ありならQuality 63.6%と価格36.4%、価格だけなら価格100%となる。スコアがない場合は全評価属性と比較価格がない。

## 市場更新の実用条件

`.github/workflows/market-feed.yml`にはUTC 02:23、08:23、14:23、20:23（JST 11:23、17:23、23:23、翌05:23）のscheduleがある。これは設定だけではSteamへアクセスせず、現在はフィード有効化・権利参照・ソース設定が未登録のため定期ジョブはskipする。queryAction分岐にも`STEAM_MARKET_COLLECTION_ALLOWED=true`が必要だが、このアプリ設定はValveの許可を意味しない。許可・公開条件が整うまで有効化しない。

実測では131商品を30商品/ページ、5リクエストで取得した。通信制限は15秒以上の間隔、6リクエスト/実行、24リクエスト/UTC日。市場が増えた場合の概算は次のとおり（30商品/ページが維持されると仮定した算術であり、Steamのページサイズ保証ではない）。

| 商品数 | 1巡リクエスト | 6回/日スケジュールで必要な実行数 | 1日予算での見通し |
| ---: | ---: | ---: | --- |
| 131 | 5 | 1回 | 6時間ごとに5件×4回=20件/日で上限内 |
| 300 | 10 | 2回 | 1巡を分けるため、およそ12時間にまたがる。4巡/日はできない |
| 500 | 17 | 3回 | 1巡を分けるため、およそ18時間にまたがる。4巡/日はできない |

この分割中は各商品の観測時刻が違うため、同一時点の全市場スナップショットではない。名前順のページングでも市場変動による欠落可能性が残る。保存済みデータから不在の商品を削除したり、出品数0へ置き換えたりしない。削除/未出品を確定できる安定した全件スキャンの証拠が得られた場合だけ、別の明示的状態として扱う必要がある。現在のqueryActionコレクターは全件完了を保証せず、部分観測として保存・再開する。

1時間ごとは5×24=120件/日、3時間ごとは5×8=40件/日となり、131商品を毎巡するなら自主24件/日を超える。6時間は131商品の場合のみ予算上成立する。300/500商品では更新間隔を延ばすか、対象を優先する必要がある。頻度を上げるための上限突破や並行アクセスは行わない。

GitHub Actionsからの実アクセスが未実施なのは、コードや接続失敗の判定ではなく、運用ゲートと第三者の継続取得・公開条件が設定されていないためである。許可済みデータフィードが得られれば、既存`market-feed`経路で受信から検証・統合・Push・Pages照合まで実行できる。差分がなければ公開を省略する。失敗した取得は既存の正常公開データを保持する。

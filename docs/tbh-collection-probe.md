# Steam 429対策・TBH先頭ページ実測

## 実測結果

2026-10-25にTask Bar Hero（AppID `3678970`）のUSD `search/render`へ1回だけGETした。過去の同日記録と今回の共有コレクター状態に403/429の停止記録がなかったため実施した。ログインCookie、プロキシ、VPN、別アカウントは使用していない。レスポンス商品や本文は保存せず、Task Bar Cubeのキャッシュ・履歴には書き込んでいない。

| 項目 | 結果 |
| --- | --- |
| HTTP | 200 |
| `Retry-After` | なし |
| 応答時間 | 408 ms |
| 要求 `count` | 100 |
| 応答 `pagesize` | 10 |
| `total_count` | 1093 |
| 返却商品数 | 10 |
| USD価格検証 | 10/10 (100%) |
| 画像URLあり | 10/10 |
| 出品数あり | 10/10 |
| 今回の通信数 | 1 |
| 実測ページサイズでの全件概算 | `ceil(1093/10) = 110` requests |

`count=100`を送ったが、応答は10件だった。現在の実装は応答の`pagesize`と実返却行を確認し、リクエスト件数を推測で100件/ページと扱わない。今回のHTTP 200はこの1回・この時点だけの結果であり、次回も同じ応答や無制限のアクセスが可能なことを保証しない。

110 requestsを15秒間隔にした場合、最初の要求直後から最後の要求開始までの待機だけで約27分15秒（109間隔）になる。今回の1件の408msを全件へ単純外挿した場合でも約28分となり、遅延や市場変動を含めれば30分枠に収まる保証はない。さらに現行の1実行6件上限では1回で全件取得できず、複数回に分けて完全な同時点スナップショットを組み立てる方式も未実装である。したがって30分ごとの完全更新は現状実現可能と判定しない。

ローカルfixture試験は`npm run market:probe -- --target=tbh`で完了した。fixtureのテスト対象は1行のみで、USD価格、画像、出品数すべてが検証された。live試験コマンドは`npm run market:probe -- --target=tbh --live`。実行時は1ページ、1リクエストで終了し、取得行の詳細は出力・保存しない。

## 旧コレクターの通信負荷

作業前の`collect()`は`count=100`を送信しても応答1ページ目の実行数を基準に次の`start`へ進み、ページ間待機は2秒だった。全件が`N`行、1ページの実返却数が`P`なら概算は`ceil(N/P)`リクエスト。TBH今回の`N=1093`,`P=10`なら110件、従来の旧`collectPair()`経路でUSD・JPY両方を逐次取得すると最大約220件だった。v0.4の本番更新経路はすでにUSDのみで、今回もJPYリクエストを追加していない。

同一呼び出し内のページ取得は逐次`await`であり、同時リクエストは発生しなかった。一方、2秒待ち、実行件数上限、日次予算、複数実行をまたぐ停止状態は存在しなかった。更新中にページ総件数が変われば現行実装でも検出していたが、同一件数のまま並び順が動くケースを完全に証明できる安定スナップショットIDは検索レスポンスから得られていない。最終件数・`start`・ページサイズ・重複・通貨・AppIDを検証しても、このサーバー側変動リスクは残る。

失敗時はUSD市場JSONと履歴の保存前に中断する。履歴更新候補は全件取得の成功後に作るため、部分取得が履歴へ混ざらない。HTTP 403/429、通信エラー、通貨不一致、ページ不整合の場合、正常キャッシュを置き換えない。

## 追加した通信ガード

- 正規市場データはUSDのみ。SteamへJPYの別リクエストを送らない。
- HTTP開始を逐次制御し、初期間隔を15秒、通常の1実行上限を6件、日次上限を24件にした。`STEAM_MIN_INTERVAL_MS`、`STEAM_MAX_REQUESTS_PER_RUN`、`STEAM_MAX_REQUESTS_PER_DAY`で上書きできる。最低間隔は15秒を下回れない。
- 先頭ページの実サイズから全件数を見積もり、上限超過なら追加ページへ進まず取得を中止する。現状のTBH測定値は110件のため、6件上限では全件スナップショットを作らず、キャッシュを保持する。
- 各試行を送信前に`.market/steam-collection-state.json`へ記録する。403/429後は停止コード・時刻・`Retry-After`を保存し、次回実行も停止する。非JSON応答も停止状態として保存する。
- 429後に自動再試行しない。別エンドポイントへ切り替えて継続しない。停止解除は状態を確認した後の手動`npm run market:unblock`のみ。
- GitHub Actionsは従来どおり手動実行のみ。Actions concurrency groupでFX更新と市場更新を直列化する。市場定期scheduleは追加していない。収集失敗後の予算・停止状態コミットは`[CF-Pages-Skip]`を付け、失敗時だけの不要なPages buildを避ける。

## 429のリスク・ネットワーク不確実性

Steamの非公開制限値、特定AppIDの上限、15秒が安全という保証は不明である。今回の単発HTTP 200を安全値の証明に使わない。Steam側の状態、送信元IP評価、他利用者の活動などにより、同じ間隔でも403/429が起きる可能性がある。

GitHub-hosted runnerは動的に割り当てられる共有インフラで、Actionsの送信元IPは専用・固定ではない。GitHubはrunner IP範囲を公開しているが、Steamがどのように評価するかは公開されていない。そのためIPを変える方法や別runnerへの切替を回避策として使わない。GitHubの共有runnerと第三者評価の不確実性は[GitHub公式IP説明](https://docs.github.com/en/enterprise-cloud%40latest/authentication/keeping-your-account-and-data-secure/about-githubs-ip-addresses)にも記載されている。

初期の日次24リクエストは上限管理用の運用値であり、Steamの許容値ではない。今回の110件という全件見積もりに対し、日次24件・実行6件では全件更新できない。全件の安定スナップショットを保つ方針では、上限を超えたデータは公開しない。

## 商品掲載ページ方式の調査

[nidea1/task-bar-trade-centerのIssue #9](https://github.com/nidea1/task-bar-trade-center/issues/9)では、`priceoverview`と`search/render`で429になった利用報告の後、開発者が掲載ページ内のSSRデータから売買板・販売履歴を読む方式へ変更したと報告している。これは利用者の報告と当該プロジェクトの実装説明であり、Steamの正式な保証や他AppIDでの成功保証ではない。

同プロジェクトの公開コード`internal/market/fetch.go`は商品掲載ページ`/market/listings/{appid}/{market_hash_name}`を最初に取得し、`marketDataFromListingSSR()`で通貨・注文板・販売履歴を解析する。`internal/market/analysis_parse.go`ではSSRの`amtMaxBuyOrder`、`amtMinSellOrder`、`cBuyOrders`、`cSellOrders`、販売履歴値を解析する。該当するSSR情報がなければ、正確な商品名を検索語にしたHTML検索ページを追加取得して、名前一致を検証する経路がある。同コードには`itemordershistogram`と`pricehistory`用URLもあるが、SSRでデータが揃う主経路では別APIを要しない。商品ごとに主ページ1リクエスト、検索ページfallback発生時はさらに1リクエストが目安。

本件ではこの外部実装をコピーせず、Task Bar Cubeの本番収集にも適用していない。TBHの商品掲載ページを使った実通信も行っていない。現行の軽量なUSD一覧取得は、1リクエストで10出品分の価格・出品数・画像を取得した。板・成約履歴がMVP要件に含まれず、掲載ページを全商品へ1件ずつ追加するのは110ページ検索以上に負荷が高いため、現時点では一覧方式を維持する。429時に掲載ページなどへ切り替える処理は実装しない。

## 30分観測・保存量の評価

30分ごとは1日48回。1観測点のインデント付きJSONは、UTC日時、`priceCents`、`listings`で約115 bytes、区切りを含め約117 bytesと概算した。現行の履歴JSONは商品ごとに1ファイルであり、価格が同じでも取得日時の異なる観測点を保存する。以下は全商品が価格・出品数の観測対象で、各回に履歴点が1つ追加される上限寄りの論理サイズ。圧縮済みGit pack、gzip転送、実ビルド時間は測定していない。

| 商品数 | 履歴点/日 | 履歴ファイル更新/実行 | 履歴ファイル更新/日 | JSON追加量/日 | JSON追加量/30日 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 4,800 | 100 | 4,800 | 約0.54 MiB | 約16 MiB |
| 500 | 24,000 | 500 | 24,000 | 約2.68 MiB | 約80 MiB |
| 1,000 | 48,000 | 1,000 | 48,000 | 約5.36 MiB | 約161 MiB |
| 5,000 | 240,000 | 5,000 | 240,000 | 約26.8 MiB | 約803 MiB |

Gitのdelta圧縮後はこの論理サイズより小さくなる見込みだが、各30分の新しい点は履歴に残り、長期運用で履歴が増え続ける。Pagesはリポジトリへのpushごとにbuild/deployし、Freeプランの上限は月500 builds。48 pushes/日なら約1,440 builds/30日で、無料枠に収まらない。したがって現在のGit連携・静的JSON構成のまま30分ごとの本番更新を有効にするのは不適切である。必要ならPages配信と収集データ用の更新経路を分け、ビルドを集約または不要にする構成を別途検討する。ユーザー要求の範囲外の追加インフラや料金が発生する方式は今回導入しない。[Cloudflare Pagesの公式制限](https://developers.cloudflare.com/pages/platform/limits/)

## 今後の収集段階

| データ | 現実的な取得方式 | 更新・整合性方針 |
| --- | --- | --- |
| 商品発見・全体一覧 | `search/render` USDページング | 1回6 request capを超える全件取得は失敗扱い。ページ順変動を検出し、完全な一時点一覧とは断言しない。 |
| 既知商品の最安価格 | 一覧の同じ`search/render`応答を再利用 | 価格取得のために商品ページや`priceoverview`を重複要求しない。部分収集方式を導入するまでは全件成功時のみ現在スナップショットを更新。 |
| 商品詳細・板・販売履歴 | 必要な閲覧対象の商品掲載ページSSRを必要時だけ検討 | 1商品1 requestが基本、SSR不足時はfallbackが1 request増える可能性。429後の切替は禁止。 |
| 成約履歴・時系列の長期取得 | SSR販売履歴が取得可能か個別に評価 | 最安出品価格、`purchases`集計、約定履歴の意味を混同しない。必要な場合も取得頻度と保存量を別途制限。 |

複数回に分けた商品別観測へ移行する場合は、各商品に`observedAt`を持たせ、異なる観測時刻を同一スナップショットとして表現しない。オフセットページングをまたぐ市場並び替えの影響を受けるため、安定カーソル等が確認できない限り途中ページを確定データにしない。

## 未確認事項と次回の試験

- Steamの利用条件・市場データ再配布条件は確認未完了。定期取得は有効化していない。
- 試験はTBH AppIDに限定。Cube AppIDは0件のため、市場実データの応答形状は未検証。
- `pagesize=10`とUSDの値は今回の単一応答だけで観測。次回も同じ10件制限やUSD価格形式とは断定できない。
- 次回は最低15秒間隔と共有日次予算を守って1ページまでを手動試験し、`pagesize`変化、価格検証率、429/Retry-After、レスポンス時間を比較する。前回からの試験回数は状態ファイルで追跡し、停止状態の解除は人が確認後に限る。
- 30分価格表示を目指すなら、商品数に応じた分割観測、各商品時刻、Pages build上限、日次リクエスト予算を含む再設計を先に行う。本番の自動スケジュールは設定しない。

# 市場更新の独立レビューと実働試作（2026-10-25）

## 結論と今回動かした範囲

取得の第一候補はGET queryAction。2026-10-25、AppID 5084200にCookieなしGETで名前順の5ページを取得し、報告総数131に対して一意な131種類を実測した。ページ間で観測時刻が異なるため、原子的な全件スナップショットとは主張しない。継続運用と旧価格との手数料基準互換性は未確認。[実測・接続手順・更新頻度評価](tbc-query-action-live-validation.md)を参照。

`market:source`でqueryAction取得・商品別保存を、HTTPSフィードと共通の検証・統合・market:publishへ接続した。外部フィードの新設は技術上必須ではない。単発検証と本番の継続取得・再配布許諾は別であり、リポジトリの運用有効化設定は変更していない。

本番向け取得元は未有効化。本番商品は0件。旧DOM実観測56件と今回のAPI実観測131件は、それぞれ別時刻の観測として隔離利用した。以下の56件E2Eはa17390時点の記録であり、今回の131件実通信とは区別する。

## 既存設計の問題と修正

1. パーサー・取込CLI・公開CLIはあったが、それらを新しい入力の到着に結びつける実行役がなかった。`market-feed.mjs`でHTTP取得から既存公開CLIまで接続した。
2. queryAction収集と公開は別の手動Actionsモードだった。新しい許可済みフィードには受信・検証・統合・公開を一つのジョブとして用意した。Steamコレクターの有効化条件は変更していない。
3. DOMデータで価格がnullだと取込拒否されていた。価格・出品数・画像が未取得の商品も保持し、価格情報なしと表示できるよう修正。未取得を0に補完しない。
4. merge時にrights確認メタデータが前のオブジェクトと参照共有されていた。コピーへ変更し、検証失敗時に入力オブジェクトを変更しない。
5. 分割再観測後にページの件数だけを表示すると保持商品数との区別が難しかった。保持56件・直近1/73件のように区別する。24時間を超えた商品観測は「古い観測」と表示する。

## 実装

`npm run market:feed -- --once` は1サイクル。`--once`なしは常駐し、既定6時間間隔で同じ処理を繰り返す。エラー時は常駐プロセスを終了し、自動再試行しない。ローカルファイル監視も隔離モードで使える。ファイルに新しい実観測が入れば統合されるが、このプロセス自体がSteamの画面を操作するわけではない。

```text
設定済みHTTPSフィード / 隔離ローカル入力
  → JSON取得（最大8 MiB、20秒タイムアウト、redirect禁止）
  → 既存market-import（AppID/USD/商品ID/時刻/価格基準を検証）
  → market-observationsの新商品・新観測を統合
  → 変更なしなら終了（書込み・Git・buildなし）
  → 本番: 既存market-publish（検証・build・commit・push・Pages JSON照合）
  → 隔離: 指定root/publicへ正常化JSONだけ保存
```

- 本番設定はリポジトリ変数`TBCM_FEED_ENABLED=true`、`TBCM_FEED_URL`、`TBCM_FEED_RIGHTS_REFERENCE`をすべて必要とする。出典は`TBCM_FEED_PROVENANCE`に固定値で記録し、権利確認参照もprovenanceへ記録する。これらの設定は許諾そのものではない。
- URLはHTTPS、資格情報やquery/tokenなし。Steamドメインは拒否し、Cookieを送らず、redirectを追わない。隔離環境のloopback HTTPだけ例外。イベント本文からURL・権利フラグ・シェル文字列を採用しない。
- 生入力はOS一時ディレクトリに置いてサイクル終了時に削除。Git/Publicへは既存パーサーが選んだ項目だけを保存する。
- 同じ観測日時・内容の再送は無変更。同一日時で内容が矛盾すれば拒否。新しい観測日時の値は、価格が同じでも新しい実観測として記録する。鮮度を偽らないため、この場合の更新は省略しない。
- 未観測商品は削除しない。商品ごとの時刻を保持。参考値は`priceMinor:null`のまま。確認済みUSD価格履歴・ランキングへ参考値を流さない。
- 出力ごとの排他ロック、既存public破損時の上書き拒否、原子的保存、既存公開CLIのPush失敗時ロールバックを再利用。公開後のPages確認失敗は失敗として報告し、成功と見なさない。ロックが残った場合は稼働プロセスがないことを確認してから復旧する。

## GitHub Actionsと無料運用

`.github/workflows/market-feed.yml`は手動・`repository_dispatch: tbc-market-feed-updated`・6時間ごとの3経路を用意。定時はUTC 02:23 / 08:23 / 14:23 / 20:23（JST 11:23 / 17:23 / 23:23 / 翌05:23）。既定はHTTPSフィード。現在はqueryActionを直接選ぶ分岐もあり、それぞれの運用ゲートがない限りjobはskipする。設定方法と失敗後の手動復旧は[実測・接続手順](tbc-query-action-live-validation.md)を参照。

FX・旧市場更新と同じconcurrency groupを使う。通常権限read、公開jobのみcontents:write。既存Git連携を使用し、Workers/KV/D1や有料契約を追加しない。

Cloudflare Pages Freeは月500build。最大4回/日で31日なら124回、日次FXを加えて155回。ソースコードのデプロイ枠も残せる。30分ごとのGit連携公開は月1,440回以上になるため無料build枠と合わない。観測頻度を高める場合は保存・公開の頻度を分離する必要があるが、今回その保存基盤の移行は行っていない。GitHub Actionsのプラン/時間枠も運用前に確認する。イベント通知を大量に送れば定時上限を超えるので、供給元と公開頻度を合意する。

Workers cronは取得処理を動かせるが、永続ストア・データ配信・認証管理が追加になる。既存Pages Git連携と無料運用の単純さを優先し、今回はActionsを選定。

出典: [Pages limits](https://developers.cloudflare.com/pages/platform/limits/)、[GitHub repository_dispatch / schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#repository_dispatch)。Actionsの定時処理は遅延・無活動時の停止があり、正確な時刻のSLAではない。

## 実データによる更新E2E

`npm run market:feed:e2e`はローカルの`.market/tbc-dom-observation-2026-10-25T10-56-31Z.json`を読み込む。ファイルがなければ失敗し、合成データで実データ成功を代用しない。

1. 元データを変更せずloopback HTTPフィードから取得 → 56商品/73件中の部分観測を検証。
2. 元の観測時刻・USD参考価格・出品数・商品リンクを保持。参考値の確定価格昇格なし。
3. 同じ入力を再取得 → 無変更、JSONバイト列も不変。
4. 隔離した模擬再観測1商品だけを投入 → 56商品維持、1商品に新しい参考価格・出品数と観測1点追加。他55商品の観測時刻は元のまま。再観測値とその時刻は試験用でありSteamの追加実測ではない。
5. 破損JSON、JPY不一致、同時刻で異なる値、HTTP429、HTMLの各ケースで以前の正常JSONがバイト単位で不変。失敗ごとに1要求だけ、再試行なし。
6. 初回と更新後にVite本番build、隔離bare GitリポジトリへのPush、模擬Pages配信ディレクトリへの反映・JSON内容照合。
7. 実ブラウザーで初回56件、Sturdy Bracelet 15%の$0.03～/17件、模擬更新後$0.29～/24件と個別時刻、他商品・検索・比較を確認。

レポートと配信用buildはGit対象外の`.market/feed-preview/`へ保存する。`initial-site`は実観測そのまま、`site`は1商品の模擬再観測を含む。模擬値は本番へPushしない。GitHub/Cloudflare本物への商品公開成功を意味しない。

今回の実行結果は、既存を含む自動テスト103/103成功、型チェック・Vite build・市場キャッシュ・FXキャッシュ検証成功。既存`market:publish:e2e`も30商品/6ページ、再送無変更、再観測、Push失敗時復旧、Pages確認失敗の検出、HAR認証情報の除外を通過した。フィードE2Eは実データ56件、模擬再観測1件、旧観測55件維持、5種類の失敗保護、模擬Push/Pages成功。loopbackへの試験要求8件、Steam要求0件。
